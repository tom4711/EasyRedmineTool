# Persistence remediation (#47 storage, #52, #56)

`AppSettingsService` now keeps a defensive in-memory snapshot. `Load`, `Save` and `Update` perform no file I/O. The constructor also performs no file I/O. Initialization reads asynchronously once, and a serialized background queue performs atomic file replacements. `FlushAsync` waits for already queued writes and reports an observed failure; background failures set `LastPersistenceError` and raise a credential-free `PersistenceFailed` event. Initialization and flush cancellation cancel only the caller's wait, not shared work.

Startup should await `InitializeAsync` before constructing view models. For compatibility, an initial synchronous `Save` on a fresh service immediately publishes the supplied snapshot and initializes in the background before writing. Initialization still checks an existing source before any write, so this compatibility path cannot overwrite unreadable settings. Callers must flush before relying on disk durability, including temporary-file test cleanup.

Schema version 3 separates small settings from immutable `settings.json.tickets.<identity>.<revision>.json` snapshots. Small settings contain the committed `TicketCacheRevision`; cache documents also carry their matching revision. Ticket changes write a new revision completely before atomically committing its reference in small settings. The previous committed revision remains intact until the settings commit succeeds, so failure or process interruption before that commit leaves the previously referenced settings/cache pair coherent. After success, cleanup retains the current and previous committed revision for that identity and removes older owned revisions. Pending/uncommitted writes do not advance committed history. An optional `TicketCacheHistory` map in small settings preserves the two committed revision references per identity across restarts and connection changes; earlier schema-3 documents without this map remain compatible. Cleanup requires an exact own filename, a validated GUID revision, and matching connection/revision metadata; unrelated files, other contexts, unversioned legacy sources, and unreadable or corrupt candidates remain untouched. Cleanup failures only log a generic warning and never reverse a successful settings commit. Initialization and the complete writer transaction (refresh committed history, create/reuse revision, commit settings, prune) acquire an exclusive OS-backed `.lock` file lease. The persistent lock file is never deleted, avoiding separate-inode ownership races. Contention retries asynchronously for up to five seconds and then uses the normal persistence error path. Every writer refreshes the latest committed history under the lease and regenerates a locally cached revision if another instance already pruned it. Small settings retain last-writer-wins semantics across instances; the guarantee is a valid matching snapshot reference. Identity is SHA-256 over a length-prefixed normalized URL and the exact API key; filenames contain no raw URL or key. Normalization folds scheme/host case and default ports and ignores trailing URL slashes while preserving path case and exact key bytes. A URL/key change clears active tickets, favorites, last ticket IDs and custom field defaults. Key rotation deliberately creates a new scope because account equivalence cannot be established offline. Prior cache files remain scoped to their original identity; changing credentials does not restore an old active view. A subsequent restart reads only the current identity's profile. Small settings updates compare ticket values, reuse the existing revision, and neither serialize nor rewrite the ticket file when unchanged. A fully written uncommitted revision can be reused by a subsequent queued retry.

Legacy combined JSON (schema 1) and the earlier split-file layout (schema 2) migrate by writing a new scoped ticket revision first and then atomically replacing the small settings file. Existing schema-2 cache files are retained. A corrupt/unsupported settings document, unreadable source, missing referenced schema-3 revision, corrupt active cache or mismatched cache identity/revision blocks automatic writes for the lifetime of that service. The source is retained byte for byte; restoration requires correcting the file and restarting. There is no automatic reset or deletion of a failed source.

Verification used isolated temporary files only, with no actual application settings or Redmine requests. The initial RED run reproduced snapshot rereads and stale data after connection changes (2 failures). Additional RED regressions reproduced first-key isolation and malformed null ticket elements (2 failures); both were corrected. The persistence suite passed 32/32 tests, covering legacy migration/restart, schema/read failures and preservation, retained-reference protection, concurrent updates, background failure reporting and isolated contexts. Review identified a second-write transaction gap in the initial split-file design; the initial deterministic filesystem regression moved the committed settings aside and placed a directory at its path so the ticket write succeeded and the settings replacement failed. Before the correction, restarting with the preserved settings loaded ticket 99 beside favorites for ticket 42. Immutable revisions now preserve ticket 42 and its matching favorites/last IDs; a later Update/Flush commits ticket 99 and its matching metadata. Three added regressions were observed RED and then GREEN for that failure, schema-2 migration, and a missing referenced revision. Three further retention regressions were observed RED on unbounded file counts, then verify that repeated successful changes retain only two owned revisions, restart and small updates preserve the prior commit, failed writes do not prune either committed revision, retries prune obsolete/orphan files only after success, and unrelated documents or connection profiles remain byte-for-byte unchanged. A final two-live-service regression reproduced the stale-history race (R1 → first service R2 → second service R3 → first service small update), where restart previously found a missing revision; after exclusive writer coordination and refreshing committed history it passes with a valid ticket/favorites pair and at most two retained revisions. Once coordination refreshes the on-disk document before writing, a directory-blocked destination is rejected earlier in the transaction and the original source remains unchanged.

The 3,000-ticket regression records zero ticket-cache rewrites for a theme/favorite update using an unchanged file timestamp and exactly the same single cache filename and verifies that the small settings document does not include ticket subjects. A measured run returned synchronously from `Update` in 0.979 ms; this is service return latency on this machine, not a desktop frame-time guarantee. The corresponding test completed in 99 ms including temporary-file setup and asynchronous writes. Snapshot-only `Load` is also verified by replacing the on-disk settings with malformed data after initialization: later loads keep the initialized snapshot.
