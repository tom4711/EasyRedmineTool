# Independent storage and transport review

Reviewed the working-tree changes for issues #47 (storage), #52, #53, #54, #56 (storage), and #58 against the architecture review and remediation plan. This was a source and regression-test review; tests were not rerun. The implementation agent reports 32 persistence tests passing after the final writer-coordination correction, 40 transport/cache tests passing, and an earlier full suite of 177 Core plus 2 Desktop tests passing. The final release suite is owned by the coordinating agent. UI and series behavior are outside this review.

## Resolved finding

**P2 — Commit a reference to an immutable ticket snapshot instead of replacing the active cache before settings. Fixed on focused re-review, 2026-11-02.** The initial implementation at `src/EasyRedmineTool.Core/Services/AppSettingsService.cs:170`–`184` wrote the new ticket list to the active identity's existing file before replacing the small settings document. Each replacement was atomic separately, but the pair was not a committed snapshot. Starting with persisted `LastLoadedTicketIds=[1]` and cache `[1]`, loading a different filter could produce IDs `[2]` and cache `[2]` (`TicketCacheMerger` deliberately prunes nonfavorites). If the cache replacement succeeded and the settings replacement failed or the process exited between them, restart combined old IDs `[1]` with cache `[2]`; the previously durable ticket list disappeared even though the update never committed. Favorites removed in the pending snapshot could similarly retain an old ID with no cached ticket after restart.

The corrected writer in `AppSettingsService.QueueWrite` creates a new GUID revision with overwrite disabled, then atomically commits its reference together with the matching small settings. Current and previous committed revisions are retained. Initialization reads only the committed identity/revision pair; invalid or missing schema-3 references block writes instead of resetting the cache. The serialized writer may reuse a fully written uncommitted revision after a failed settings commit, without changing the prior committed pair.

The added `Failed_small_settings_commit_preserves_previous_ticket_snapshot_and_retry_is_coherent` regression deliberately makes only the settings replacement fail after the cache write. It restores the previous settings document, restarts, and verifies the previous ticket, favorites, last IDs, and unchanged prior cache bytes. It then retries through `Update`/`Flush`, restarts again, and verifies the new coherent pair. Separate regressions cover schema-2 migration and missing referenced revisions; existing schema-1 migration coverage remains. Source inspection confirms that this closes the original transaction gap for the writer. The later retention refinement is reviewed separately below.

## Retention refinement: resolved finding

**P2 — Cleanup can delete a revision still owned by another running settings service. Fixed on final focused re-review, 2026-11-02.** The first cleanup refinement derived committed history from this instance's dictionary and deleted matching files outside that local current/previous pair. It had no exclusive ownership across settings-service instances or app processes.

Concrete original sequence: A and B initialize the same settings path at revision R1. A commits R2 and retains R2/R1. B commits R3 using its earlier R1 history, then cleanup retains R3/R1 and deletes R2. A's next theme/favorite update reused `_writtenTickets` R2 without rewriting it, then committed settings referencing the missing R2. A later restart reported a missing active profile and blocked persistence. This did not require simultaneous file operations; sequential updates from two open app sessions sufficed.

The final correction acquires a shared-path `FileShare.None` lease in `AcquirePersistenceLockAsync` (`AppSettingsService.cs:219`). Initialization holds it across the settings/cache pair read. The writer holds the same lease across refreshing committed history from disk, creating or checking a reusable revision, committing its reference, and cleanup (`AppSettingsService.cs:179`–`210`). The existence check and possible regeneration of a locally remembered revision therefore occur within exclusive ownership, closing the deletion window. The lock file remains present after release so another writer cannot acquire a different inode at the same path. Lock acquisition has a bounded asynchronous retry; failures follow the existing persistence-error path.

The refinement delays cleanup until settings commit succeeds, retains current/previous committed history, skips unrelated filenames/payloads/identities, and catches cleanup failures. Its three retention tests cover those properties. The added `Two_live_services_refresh_committed_history_before_pruning_or_reusing_a_revision` regression executes the original A/B/A failure sequence and verifies successful restart, matching ticket/favorite data, and bounded retained revisions. Source inspection confirms that the final coordination mechanism resolves the reported blocker. Independent test execution was not part of this review.

## Other reviewed behavior

- Startup awaits initialization before constructing view models. Initialization and queued writes do not form a self-await cycle: migration queues its write without awaiting it, and that writer waits for initialization to finish. Preinitialization `Update` remains a caller precondition; the production startup satisfies it.
- Settings snapshots and queued data are defensively cloned, including nested ticket entities and custom-field defaults. `Update` serializes concurrent callbacks under one lock, and the write queue preserves their order.
- Corrupt, unsupported, unreadable, or mismatched active sources block automatic writes and retain their source bytes. Legacy migration writes cache data before replacing the combined source. Background errors are observed and reported without exposing raw settings.
- Connection identity includes normalized URL and exact key. Credential changes clear active connection data; a new identity cannot read the previous identity's ticket file. Switching back deliberately does not restore an old active view.
- Both cache implementations detach old inflight tasks on invalidation and guard publication and removal with the captured generation. New readers cannot share an earlier generation, and old completion cannot remove the current load. Cancellation belongs to individual waiters; shared GET operations continue.
- Pagination advances by received records, respects reported page size when no total is supplied, detects duplicate records and unexpected nonzero offsets, and fails explicitly for premature exhaustion or the safety limit. Both endpoints share this logic. Time-entry query dates use invariant Gregorian formatting.

Both reported findings are fixed in the reviewed source. No unresolved concrete correctness, data-loss, or concurrency blocker remains in this scope; final test results are supplied separately by the implementation/coordinating agents.
